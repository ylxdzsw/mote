# Cloud workspace

Mote is one private workspace protected by the existing `nginx_auth` cookie key. Everyone with the key has the same access. There are no user accounts, roles, editable share links, or collaborative merging yet.

## Documents and local work

- `/` opens **Files**; `/d/:id` opens a stable document URL: editing on desktop, chrome-free authenticated reading below 768px. Mobile has no Files navigation inside a document; browser Back or `/` returns to file choice. The reader uses the existing workspace cookie, never an automatically created public token. Nginx serves the existing server-wide `/var/www/login.html` at the requested URL when the cookie is missing or invalid, matching the other protected apps. The shared login sets the cookie and reloads that same URL; Mote does not bundle its own login page. APIs return JSON `401`, not login HTML. Expired authentication never intentionally discards local edits.
- **Files** opens, creates, imports, renames, archives/unarchives, and deletes documents. Names need not be unique and are separate from authored Title paragraphs. Renaming preserves URLs. Importing a `.mote` file always creates a new document with a fresh ID. The filename, without its extension, supplies the new cloud name; invalid files leave the workspace unchanged. The former browser draft remains available for recovery; unsupported formats are not converted or automatically uploaded. Each unarchived row menu places Archive between Rename and Delete; archived rows show Unarchive in the same position. The **Archived** group shares a compact bottom-aligned disclosure stack with **Local recovery**; both expand inline and start collapsed each time Files opens; both groups share search and row actions, sort within each group, and search does not expand Archived. The main count covers matching unarchived files; the archive heading counts matching archived files. Archive actions need no confirmation, and a row moves only after server acknowledgment. The current document stays open, and opening or editing an archived document does not unarchive it.
- Archive is false by default and server-owned metadata, with its own monotonically increasing `archiveRevision`, independent of content revisions and `updatedAt`. `PUT /api/documents/:id/archive` accepts `{archived,baseArchiveRevision,operationId}`; the revision compare-and-set and operation ID make concurrent changes explicit and uncertain retries safe. Committed changes use the existing document/metadata SSE invalidation. Replaying an acknowledged operation returns current metadata without reapplying the old change. Archive does not change native content/version, content history or undo, the or modified timestamp; content saves cannot reset the flag. New, imported, and Save as copy documents are unarchived, and exports omit archive state. Archive changes only Files organization: synchronization, sharing, Private, AI tasks, and existing access rules continue unchanged.
- **New** opens a blank file form for Name, Appearance, Text language, and Private. Cancel creates nothing. Submitting all untouched defaults starts a local-only working copy with a stable ID, not a cloud record. Remembered appearance/language become its browser-local blank baseline, so these defaults alone do not retain an empty file. Entering a name or changing any form field, even reverting it, retains the file through an immediately queued, retry-safe first create. Content (including Notes, objects, or explicit structure), subsequent document settings, or a submitted AI request also retain a draft. Private selected in the form is included atomically in the creation body; it is shown as pending until acknowledged and blocks sharing/external handoff locally meanwhile. Imports always start saving immediately; existing cloud files are not auto-deleted when emptied. Draft URLs can reopen only where their browser-local copy is available until their first cloud save; clearing browser storage loses local-only drafts.
- Every tab has a separate IndexedDB working copy. A session-identity Web Lock prevents duplicated tabs from writing the same record. The lock does not grant exclusive document editing. Without Web Locks, sessions always fork and previous dirty copies remain in **Local recovery**.
- Changes save locally promptly. The active document autosaves every 30 seconds while dirty (clean copies skip the autosave), on the sync indicator, and on Ctrl/⌘S. Offline mode pauses ordinary cloud requests while local editing/saving continues. The indicator retries a validated read-only connection check; while offline the open document also probes every ten seconds and on the browser's online event. Successful reconnection resumes synchronization and AI result monitoring without resubmitting generation. Invalid responses (including Wi-Fi login HTML) never acknowledge a save. Switching documents attempts a sync when connected and requires successful local preservation before leaving. Inactive documents do not continuously sync.
- A cloud save compares its base revision atomically with the current revision. An operation ID is persisted before sending, so a retry after a lost response can recover its original acknowledgment. Edits made during a request remain pending and are drained by the next save.
- A draft’s first save persists the exact creation body and operation ID before its POST. Uncertain creation replays that same operation before draining newer edits through revision-checked saves; reloading or recovering a draft must not replace its unacknowledged creation body. Imports use this same pending-create working-copy path: the imported file opens locally first, then sync confirms its cloud creation. A failed or uncertain import retries through sync or Local recovery, not another import.
- **Synced** means an acknowledged cloud save; **Changes pending** means edits await cloud synchronization. Local writes start promptly, but **Saving locally…** appears only after a local save remains in progress for 500 ms, regardless of what caused it. Offline uses the same delay and otherwise shows **Offline · changes pending** for unsynced edits. Pending work is not a cloud backup. Cloud failure, sign-in, conflicts, deletion, and local-save failure retain distinct feedback; local-save failure appears immediately and warns before leaving.
- A conflict pauses automatic sync. **Save as copy** creates another file; **Discard local changes** fetches the latest cloud content; **Overwrite cloud version** still checks the exact version shown to the user. If that version changed again, it conflicts again. Overwrite directly replaces the current cloud version; it creates no extra recovery copy. Save as copy persists its destination working copy and the original’s retry link in one IndexedDB transaction before creation. Retrying after a lost response or reload uses the same destination and first chosen filename; newer edits drain afterward. The original stays recoverable, and independently edited destination copies are never silently overwritten.
- **Local recovery**, expanded inline at the bottom of Files, lists pending or unsupported working copies, including those from closed tabs and copies with pending assistant input even when the document itself is synced. Opening a recognized recovery carries its working-copy checkpoint into the new tab without changing pending operation bodies or IDs. It never replaces another local pending checkpoint; use a new tab when necessary. **Download recovery** preserves raw working-copy JSON and its local assistant checkpoint and attempts to include available cloud assistant state; unavailable sources are identified, and a network or assistant-storage failure does not prevent downloading the working copy. This remains general working-copy recovery, not a way to import legacy task records into current Assistant state. Assistant no longer has a retained-task or recovery-archive UI; legacy records are left in storage. The earlier browser-only draft is download-only. There is no server recovery-copy browser, merging, or conflict-comparison renderer. Immutable revisions used by AI inputs and request acknowledgments are separate from overwrite recovery.
- A deleted document is tombstoned, all its links are revoked, and stale tabs cannot resurrect it through autosave. Their local work can be saved as another file or explicitly discarded.
- Undo/redo remains an editing-session history in memory, not a cloud-wide stack. Sync does not clear it; undo after sync makes a new local change. Reload and adoption of remote content clear history. Undo history is never exported in `.mote`.
- Optional `authoring.notes` in V1–V3 stores an ordered array of user-maintained plain-text scratchpads. Notes save in the same document revision, local recovery, and native `.mote` exports. If `authoring` is omitted there are no notes or document model override. Notes are outside the rendered page and hidden in reading mode. Public shared responses and HTML export omit the entire `authoring` object; PNG only renders the page.
- Clean private editors can adopt newer server revisions; dirty copies are never silently replaced. Browser recovery can be evicted or cleared, so unsynced work is not durable cloud storage.
- Each mounted cloud document owns one authenticated `GET /api/documents/:id/events` SSE connection per tab, shared by content/metadata (including archive), privacy, assistant recovery, task status, and live transcripts. Committed mutations publish scoped invalidations; reads never publish update feedback. Initial connection and reconnection reconcile current state, and consumers retain notifications arriving during an in-flight read. Healthy document/assistant/task reads do not poll. Only a viewed transcript requests bounded JSON history. Document deletion ends its stream; switching documents and service shutdown close connections. Public shares and local previews do not subscribe.

## V1–V9 documents and layout

V1 is the original continuous-page format. V2 adds optional Slides to the same closed `MoteDocument` schema. Older versions migrate on load as described in [Format versioning](#format-versioning-and-unsupported-records). V3 adds optional table color pairs without changing older styling. V4 restricts theme font weights to Regular (400) or Bold (700). V5 adds permanent image/widget markup; V4→V5 is non-breaking and leaves existing content unchanged. V6 adds optional document-level `theme.justifyText` (omission means false); V5→V6 is non-breaking and changes only the version. V7 adds optional document-level `theme.firstLineIndent` (omission or false means no indent); V6→V7 is non-breaking and changes only the version. V8 adds semantic Separator paragraphs in main text and Text objects, plus optional `theme.paragraphs.separator.lineThickness`; V7→V8 is non-breaking and changes only the version. V1–V7 reject the Separator semantic and `lineThickness`. Separators are not valid in table cells or owned captions and are not objects or layout choices. V2–V8 decks use `page.slideHeight` with optional top-level `slideBreak` atoms. V9 is continuous only: the breaking V8→V9 migration removes authored crops and boundaries. It also simplifies inline Box marks and makes the document typography switches explicit. The complete field, rich-text, theme, layout, ownership, coordinate, and validation rules are normative in [FORMAT.md](FORMAT.md).

Cloud storage and APIs use the same V1–V9 `MoteDocument`; there is no V0-shaped runtime adapter. Objects are stored in ordered `objects` with all saved geometry nested in `layout`. Flow atoms remain first-class main-content blocks, and a Flow object's position comes from its matching atom rather than saved anchor/y/centering fields. Floats retain main-block anchors; Flow-relative Float offsets are signed on both axes, while ordinary anchor y offsets are nonnegative. Legacy floats anchored to removed slide boundaries receive estimated continuous positions during migration.

Captions are owned subobjects on image, HTML, and table objects. They remain below and centered on their owner and participate in the owner's composition, reservation, segment, layout, and export behavior. Clipboard and AI segment compositions preserve block/object/anchor relationships and remap IDs on paste. Individual AI object revisions preserve user-owned margins and caption width; section reservations lock their composition. The renderer and measured Flow mounts are shared by editing, reading, minimap, PNG, and standalone HTML.

## Preview and reading

Preview opens `/preview` in a separate tab/window and transfers a snapshot of the current working copy over a browser-local message port. Unsynced edits are included; `authoring` and unaccepted AI candidates are excluded. It does not synchronize, upload a snapshot, create/revoke sharing, or issue a capability. Private documents can be previewed. Clicking Preview again replaces the snapshot in the same reader window when available; opening `/preview` directly or reloading it does not restore a snapshot. First opening needs the app assets. Mobile authenticated documents, public shares, and Preview use the same `ReaderPage` over `ReadDocument`/`DocumentCanvas`, with automatic minimap behavior and no title, Files, or Edit toolbar. Private sync/recovery errors remain actionable. HTML download is a separate, static publication of the shared render, not an import format.

## Sharing

Public sharing is disabled for new documents. The Share dialog's **Link** tab controls at most one active, latest-version link per document. Opening the dialog reads the server-owned share state but never creates a link. For the open document, enabling first synchronizes its working copy; if synchronization fails, no share is enabled and no URL is issued. Files → row menu → Share opens this same dialog for any document without navigating. For another document, enabling uses its already cloud-saved content, never syncing the active document or adopting another tab’s recovery copy. Once enabled, the tab shows the URL and **Copy link**. **Replace link** asks for confirmation before revoking the current token and issuing a fresh URL. **Disable sharing** also requires confirmation; confirmed revocation is permanent, and enabling later creates a new URL. Copy, replace, and disable have no document-save prerequisite. Share state is server metadata, not document content, undo history, or export settings.

Share state has its own server-owned revision. `GET /api/documents/:id/shares` returns `{revision, share: null | {id, token}}`; `PUT /api/documents/:id/shares` accepts `action: "enable" | "disable" | "replace"`, `baseRevision`, and `operationId`. Each operation atomically compares the base share revision, and operation IDs make uncertain retries safe. There is no link-list endpoint or snapshot-creation `POST`. These operations do not change document or AI revisions.

Links use 256-bit random tokens at `/s/:token`, work without login, and mount the read-only canvas. Opening a public link makes one scoped document fetch of the then-current cloud revision; unsynced local changes are not included. The reader does not poll, use SSE, announce updates, or refresh automatically. Later cloud saves appear after reload, which fetches the then-current document. The entire `authoring` object is omitted from the public shared response. Interactive widget code may independently load network resources; sharing does not archive external dependencies or runtime state.

Revocation and file deletion stop future access, not copies already opened or downloaded. Shared APIs expose only the selected document, filename, and current revision, never AI state or other files. Public navigation uses no-referrer/noindex/no-store headers. Nginx access logging is disabled for both `/s/` and `/api/shared/` so bearer tokens do not enter ordinary access logs; upstream logging needs the same care. Sharing is read-only even when the visitor holds the workspace cookie. Public-share links are independent of task tokens and reservation expiry.

### One-off share decisions for format migrations

Keep links by default. For each native migration, decide whether the new interpretation materially changes what the owner published. If it does, revoke links for the affected **stored, pre-migration documents** before serving that interpretation. This policy is independent of breaking-format classification, is not native document data, and introduces no resumable or paused links.

V2–V8 migration steps keep links. V8→V9 permanently revokes an existing latest link if the current stored revision is a deck (`page.slideHeight` present), even if nothing actually overflowed. Continuous documents keep their link and share revision. Removing a slide crop can make content visible that was already present in the fetched payload; the crop was never an access-control boundary.

Before opening its listener, the service inspects active links and atomically commits each affected link’s revocation and its document’s share revision increment. It never rewrites document revisions or changes reservation state. Revoked links no longer match the check; no migration ledger is needed. Old tokens stay unavailable, and a retried share operation returns today's state rather than resurrecting its old token.

Legacy clients can still save supported native versions. If a save introduces a deck behind an active link, the same content transaction revokes the link and advances its share revision. Enable/replace will not issue a link to a stored deck: the owner must open and save its converted continuous layout first, then explicitly enable a fresh URL. Restarting the service does not revoke that new link.

Only latest-version links are supported. Historical snapshot-share database migration is not maintained; recover an older database with its matching build and export documents rather than expecting the current service to upgrade its share rows.

## AI is document-associated

The current agent protocol is `mote-agent-v7`, distinct from native document versions V1–V9. No protocol/history adapter or automatic conversion is required. Existing legacy task records and artifacts are left untouched; the current client does not import them into active reservations/tasks or show a task-recovery archive. They are not continued, resubmitted, accepted, or converted by the current service. General Files local recovery downloads remain. Native document compatibility remains V1–V9.

### Two current systems

Current editing state is `{document,reservations}`. Cloud document reads return the native document and its separate reservation list; create/save writes both atomically under one document revision compare-and-swap. Reservations are not native JSON, `.mote` exports, or publication payloads. Their optional `expiresAt` and spatial-instruction `markup` properties are part of document undo/redo. Markup stores strokes/labels and target-relative document-pixel coordinates, never a background capture; the task description returns the latest saved value. It neither changes the native document nor expands the reserved write scope. Each reservation ID is its task ID. A separate 128-bit random task token is generated by the server, is never editable/imported/exported, and remains stable across saves and reservation removal/restoration. Current release is omission from the reservation array, not token revocation: for an undeleted, non-Private document, a committed omission follows the existing capability 404 path; Undo followed by an ordinary save restores the same reservation and token. Private on/off behavior is unchanged.

Task execution, proposals, versions, idempotency receipts, transcripts, and Mu continuation artifacts are separate server-side data from document/reservation state. The server lazily ensures a waiting task on owner `GET /api/ai/tasks/:id` once its reservation is cloud-committed. A built-in run starts only after `POST /api/ai/tasks/:id/revise`; an external agent may use the task token. A reservation-only draft, even for an otherwise blank document, is retained and published by ordinary cloud sync. Current task artifacts and versions are not automatically deleted or expired after Accept/Discard; this server retention is independent of the browser cache described below and does not mean local cache pruning removes server data.

Reserve, reservation-property changes, Accept, Discard, and deleting a reserved target are ordinary local undoable edits. Accept applies the selected cached proposal; Accept, Discard, and deletion remove the reservation from the current array in one history change. They make no task-service request, cloud preflight, or immediate sync. Current releases are represented by absence, not by persisting `released:true`. Undo/redo restores prior snapshots, including the same task ID and token, and never regenerates. Reservation changes schedule an opportunistic 650ms debounce to the ordinary sync path. Normal autosave, retry IDs, and revision CAS are unchanged; cloud authority is the last committed document/reservation state. The final save validates the native document and CASes the observed revision. Older explicit `released:true` reservations are stripped when history initializes and disappear from cloud state on the next ordinary save.

A cached proposal remains available for Original/Preview and Accept during task-service or network failure while its task remains referenced by the working copy's current state or undo/redo history. Preview and Accept check the candidate against the actual current document and reservation scope; they do not compare against an immutable original-content snapshot or require fresh task status. A failed final save follows ordinary conflict/recovery behavior and preserves local work. No acceptance or discard permanently revokes a current task token or writes a permanent revocation tombstone. Once the reservation's absence is committed, task-capability requests follow the existing 404 path, subject to the Private/deleted-document access gates; restoring the reservation and syncing it makes the same token usable again. Server task artifacts and versions remain retained after Accept/Discard, even when the browser has pruned its local cache.

Browser cache retention is per working copy. A task's local view/proposal/draft cache is retained while its ID is present in the current reservations or any past/future history snapshot; undo history is capped at 100 entries. After the corresponding working copy is saved locally, cache entries with no history references are pruned. Dropping the redo branch or evicting an old undo entry can therefore trigger pruning. On unmount and on the next open, which has no persisted undo/redo stack, cache is trimmed to current reservations. Failed local saves do not prune it. This is not a server garbage-collection signal: an independent or offline tab may still reference the task, and server task artifacts/tokens are retained. There is no promise of complete task or disk cleanup.

Built-in and External tabs in Assistant are local UI choices only: they do not make a backend executor assignment, issue/revoke credentials, or stop execution. Multiple built-in and external agents may act concurrently and append to the same sequence. `POST /api/ai/tasks/:id/stop` stops built-in execution only; an external agent can still submit while a built-in run is active or stopped. The same task token and version history serve both.

### Owner and agent APIs

Authenticated document create/save APIs carry the native `document` and a separate `reservations` array. The document and reservation list commit under one CAS. The former `/api/documents/:id/assistant` state is GET-only access to older stored task records; writes are not a current task path. The current client does not import those records into active Assistant state or show a task-recovery archive, and it leaves the stored records untouched. General Files local recovery downloads remain separate. Current owner task routes are:

- **GET `/api/ai/tasks/:id`** lazily ensures and returns task status/proposals for a committed reservation.
- **POST `/api/ai/tasks/:id/revise`** accepts `{prompt,operationId,model?,selectedVersion?}` and starts a built-in execution with retry-safe `operationId`. There is no executor revision or generation authorization parameter.
- **POST `/api/ai/tasks/:id/stop`** stops that built-in execution only. `/executor`, `/workspace-read`, and `/release` mutations are obsolete and return 404.

Agent resources are relative to the stable public `/a/<22-character-base64url-token>` URL or the supplied task-local built-in Unix socket. Public `/api/agent/` remains retired; the built-in socket exposes only the scoped agent resources. External requests do not need a workspace cookie or Origin. Tokens must not enter logs, document content, task exports, or citations. Static `/skills/` files are grant-independent and contain no task data.

`GET` of the task base URL returns the canonical JSON description: `protocol:'mote-agent-v7'`, task ID, request/feedback, exact `.target`, segment `.geometry` measurements, optional `.markup` spatial instructions, optional expiry, and skill/helper/schema/resource URLs. It excludes copied original content and snapshots. Separate `manifest.json`, `target.json`, and `instructions.md` routes return 404. The task token is separate from task ID. `GET document.json` is optional and returns the latest authorized cloud document at access time, including document revision metadata; it is not pinned to a task or read history. A requested historical revision query has no effect on the current agent route. The task cannot select a different document by ID.

`GET versions.json` returns one flat append-only sequence of `{id:'V1',label?,candidate}` records. Individual `versions/V1.json` resources expose the same immutable proposal. IDs are assigned in submission order. A version has no `origin`, agent, parent, lineage, document revision/version, or per-version revision. Concurrent built-in/external submissions share the sequence. A successful POST receipt is exactly `{taskId,versionId,status:'ready'}`.

`POST submit` accepts `{operationId,candidate,assets?,label?}`. It accepts no document revision, executor, execution generation, or source/origin field. The operation ID and payload provide retry identity; an identical retry returns the prior receipt, while reusing an ID with changed input is a conflict. Delivery validation is deliberately stateless: it checks the current proposal grammar and embedded/uploaded assets, without a document, target, source version, agent origin, or session. The current native V9 payload grammar applies at submission, regardless of the native version of the document being edited. `public/skills/proposal-schema.json` advertises `documentFormat:"mote"` and `documentFormatVersion:9` only as advisory schema metadata; these fields are not submitted, echoed, or proof of a document read. Invalid proposal errors include the schema URL and JSON path where available. Owner Preview/Accept validates applicability against the actual document/reservation; the ordinary final document save performs native validation and revision CAS. Candidate submission never changes document content or auto-applies a proposal.

Segment `objects` entries may be complete native objects or bare safe IDs. Delivery preserves IDs and validates unresolved grammar plus explicit payloads; it never reads document objects to expand them. Preview/Accept requires each referenced ID to belong to the reservation and exist in the current working document, deep-copies it literally, then performs ordinary complete-candidate validation/application. Missing/out-of-scope IDs fail. There is no merging, coordinate adjustment, snapshot fallback, automatic retention, or changed ID semantics. Cached review remains local/offline. The native document and exports never contain these strings.

HTML screenshot paths are names in the supplied assets map, not server paths or URLs to fetch. Embedded/native images remain embedded. Candidate validation does not execute widget HTML. `BASE OUTPUT [LABEL]` is the portable helper interface; its durable operation IDs are keyed to the base URL and exact prepared payload/label, with private sidecars in the output directory. It submits no executor or source-revision metadata. Keep sidecars with the output and repeat the same command after an uncertain response.

### Task access

Each agent resource GET checks the current saved reservation at request opening. Each submission checks active/released state and optional `expiresAt` once at request opening; an already-authorized in-flight submission may finish harmlessly after a later reservation removal or expiry. There is no 24-hour owner-inactivity window, keepalive, access pause, or HTTP 423 lifecycle. An absent `expiresAt` means no time-based expiry. A missing reservation follows the existing not-found (404) path; an expired active reservation is rejected at request opening, and older explicit `released:true` records retain their legacy 410 rejection behavior. A missing/deleted document remains blocked by the ordinary document boundary. A Private external request is denied (HTTP 403) for every public `/a/` method. The stable token itself is not rotated or permanently revoked by Accept/Discard, Undo, or a Private toggle.

Both agent transports can read only the document containing the reservation. The retired `workspace-index.md` and `workspace-document.json` resources return 404 for authorized requests. Old reservation payloads may still contain `workspaceRead`; it is ignored and grants no access, including on an exact pending-save retry.

Private blocks the public `/a/` endpoint for all methods while enabled, including reads and submissions. It does not erase the task token. If Private is later disabled, the same active, unexpired reservation token works again. The trusted built-in socket may read its own Private document. Private remains distinct from public Share: turning Private on permanently revokes the active latest-version Share link, and turning it off never restores that public link. Already downloaded data cannot be recalled.

A task URL grants only task-scoped reads/submissions; it cannot save the document or accept proposals. A submission never changes a reservation, and only the owner can apply/release via document edits. Old `/assistant` task records and artifacts remain stored and read-only; the current client does not import them into active state or present a recovery archive. No current protocol adapter or task-history migration is required. Current server task artifacts are retained after Accept/Discard rather than automatically removed; this does not retain a browser-visible task archive or prevent per-working-copy cache pruning.

### Built-in execution and recovery

Built-in agents use the task-local Unix socket and the same proposal resources as external agents. Each built-in run receives a run-local copy of the latest saved document as optional advisory context; socket `document.json` reads return the latest saved cloud document at the time of each request. Neither is a submission prerequisite. Built-in and external delivery share the current validator and append-only proposal list. The local Assistant tabs do not change backend authorization; Stop affects only built-in execution.

The configured workspace/document Mu model is required for generation; provider/model failures never block ordinary editing or local candidate review. Generation is never automatically restarted after connection recovery or service restart. Network failures preserve document edits, task reservations, and cached proposals while the task remains referenced by the working copy's current state or undo/redo history. Healthy document/task invalidations use the single per-document SSE stream; transcript history remains a bounded task-local read. Worker cleanup is a resource-management boundary, not a token-generation or document-revision authorization mechanism.

Owner and public endpoint responses retain `Cache-Control: no-store`; public capabilities also use no-referrer/noindex behavior. Public-share links and their existing revision/CAS/revocation policy are unchanged and independent of task token behavior.

## Widget screenshot capture

**Update screenshot** is an explicit owner action, available through the login-gated, exact-Origin `POST /api/widgets/screenshot`. The request contains only `{html,width,height}` from the local working copy, including unsynced source; it does not read a cloud document or grant workspace access. The response contains an embedded PNG in `{screenshot}`. The browser applies it as one local undoable change, then saves it through normal revision-checked synchronization. Capture does not save documents directly, call a model, or alter AI reservations. Public readers and agent capabilities cannot invoke it. Private documents support owner-requested capture under the same boundary.

Limits are 1 MiB of HTML within a 2 MiB JSON body, dimensions from 1 to 2048 CSS pixels per axis (rounded to integers), at most 2 megapixels of native area, and a 10 MiB PNG at 2× resolution. Two captures may run concurrently; additional requests receive a retryable busy response rather than queueing. Each job has a 25-second deadline plus bounded teardown; the browser request allows 35 seconds. Capture-specific errors stay local to the action rather than taking the workspace offline. A disconnected client aborts its job. Unconfirmed worker teardown fences new captures until service recovery.

Real captures use a disposable systemd service with an empty filesystem root, read-only runtime/font mounts, a fresh Chromium profile, unprivileged dynamic user, private PID/network namespaces, and bounded CPU, memory, process count, and runtime. The worker receives only the widget source/dimensions and capture harness; cloud storage, AI task directories, host credentials, and the private Mote socket are absent. Chromium keeps its own sandbox enabled and uses the same opaque-origin `allow-scripts` iframe as ordinary widget rendering.

The browser has no host-network access. A bounded CONNECT proxy permits only public destinations on port 443 for HTTPS resources, pins checked public IPv4 addresses at connection time, and checks every new destination, including redirects. Private/reserved addresses, the server's own addresses, IPv6, plain HTTP, and other ports are blocked. The browser starts without workspace cookies or credentials; any cookies or requests created by the widget stay within this disposable run. Public resources can observe requests made by the widget; capture is not an offline or network-free execution promise. Resource loading is bounded, and a fresh animation or asynchronous app may render differently from an interaction already open on the page.

Captures are transient, not durable AI tasks: no automatic retry after reconnection or restart. The previous saved screenshot survives failures; source/geometry changes, undo/redo, reservation, deletion, leaving editing, or document switching prevent late results from being applied. Existing embedded screenshots are retained, including manually supplied ones. Minimap and PNG export keep using the saved image without executing widget code. Fake development returns a deterministic PNG without starting Chromium.

## Document Private policy

**Private blocks public sharing and external agents for one document.** A non-Private document is still login-gated unless the owner creates a public Share link or hands out a task link. Agents never have cross-document access, regardless of this setting.

| Access | Non-Private | Private |
| --- | --- | --- |
| Workspace owner | Allowed after sign-in | Allowed after sign-in |
| Built-in agent on this document | Allowed | Allowed |
| External agent on this document | Requires an active, unexpired reservation link | Blocked for every public task request |
| Public reader | Requires an active Share link | Blocked; enabling Private permanently revokes the link |

Private does not disable built-in generation or prevent the configured model provider from processing the task's document when the owner starts generation. No background indexing runs for any document.

### Changing Private

Private is server-owned document metadata, separate from editable content and content undo/redo. A stale tab's content save must not reset it. Only a confirmed server update may be presented as an applied privacy change.

New documents default to non-private; the creation form and the Settings toggle on an unsaved draft select Private atomically on first creation. A confirmed creation resolves that pending choice even at privacy revision zero. If a creation operation was already persisted with an uncertain outcome, its body is never rewritten: first reconcile that operation, then apply the revision-checked privacy change. Save as copy preserves Private; native exports contain document content, not cloud access settings. Privacy has its own monotonically increasing revision and retry-safe update operation, independent of content revisions. Clients refresh it even with unsynced text and never adopt an older privacy revision from a delayed save acknowledgment.

Checking Private revokes the active latest-only public Share link and immediately blocks every public `/a/` method for that document. The task token remains stable; turning Private off restores access to the same active, unexpired reservation. The trusted built-in agent may process its own Private document. Public-share revocation remains permanent even if Private is later disabled.

When enabling Private, the editor checks whether the one active public Share link exists. If it does, one confirmation warns that the link will be permanently revoked and turning Private off will not restore it. The privacy request carries the observed sharing revision; a concurrent sharing change rejects the update and requires reviewing Private again rather than revoking a newly issued link. Cancel leaves privacy and the link unchanged; a failed share-state check does not proceed with the change. No confirmation is shown when there is no active link or when disabling Private. Enabling Private does not permanently revoke the task token.

Private does not switch a task to Built-in or revoke its token. Each public task-resource request, including every HTTP method, checks Private at request opening. A task-local built-in socket can still read its own Private content. Reservation release/expiry is checked at each resource opening; a submission already authorized at opening may complete harmlessly afterward.

Unchecking Private makes the existing active task token usable again if its reservation is still active and unexpired. It never restores a revoked public Share link.

Revocation governs future access. It cannot recall already fetched content, erase an agent's existing context, terminate an external process, or retroactively remove material copied into another document. Private is not a content-tracking or remote-erasure mechanism.

### Essential implementation checks

- The active latest-only public Share link is revoked permanently. Public task methods are blocked while Private is enabled; the same stable token works again after disabling Private if the reservation is active and unexpired. Its own built-in socket remains available.
- Agents cannot discover or retrieve another document, even with a known ID or a legacy workspace grant. Existing reservations and pending saves remain valid.
- Owner access through Files is unchanged, and stale content saves cannot clear Private.

## Format versioning and unsupported records

Supported versions are V1–V9, and V0 is permanently unsupported. `loadDocument` migrates older supported versions to the current one in memory through ordered, pure, ID-preserving steps, each labeled breaking or non-breaking. The breaking V3→V4 step maps explicit theme weights below 550 to 400 and weights at least 550 to 700, preserving sparse inheritance and unrelated data. V5→V6, V6→V7, and V7→V8 are non-breaking and change only the version; omitted `theme.justifyText` and `theme.firstLineIndent` remain false, preserving the prior alignment and no-indent behavior. V8 adds Separator without changing old document meaning; V1–V7 reject Separator paragraphs and `lineThickness`. V8→V9 is breaking: deck flattening is deliberately lossy, while inline Box conversion and explicit typography switches preserve meaning. The rules are normative in [FORMAT.md → Versioning and migration](FORMAT.md#versioning-and-migration). For cloud work:

- **No write on load.** Opening a document never creates a cloud revision, so a migration alone does not conflict with other tabs. The next ordinary revision-checked save persists the upgrade. Until then the stored record keeps its older version, and every reader migrates it identically. The pre-migration document stays available in local recovery until the upgraded save is cloud-acknowledged.
- **Readers.** An eligible public share fetches one snapshot and migrates it in memory with no write-back. One-off share policies apply before any public fetch. Native imports go through the same load boundary.
- **Pending tasks.** Retired agent protocols may be rejected or omitted without migration. Current-protocol v7 reservations are part of the ordinary document revision and proposals remain in separate task artifacts. A non-breaking load path leaves reservations usable. A breaking path asks the owner before migrating a document with active reservations. Upgrade removes the current reservations through the ordinary cloud document save; it does not permanently revoke their stable tokens. Restoring a reservation through a later ordinary save can make the same token usable again. Decline shows a read-only V9 preview without changing the stored document or its reservations. Neither choice retries generation; retained proposals/artifacts are not converted.
- **Unsupported data.** Newer or unknown versions and malformed records get an actionable error. They remain recoverable and are not rewritten or published. Unsupported imports leave the open document untouched.

In the client, a migrated working copy keeps the stored document in `migratedFrom` until a cloud save is acknowledged. The copy stays clean, so opening alone saves nothing; an ordinary edit or AI request persists the upgrade. Public shares load and publish the document; owner cloud reads retain the stored record. `mote-agent-v7` task reads load only the task’s authorized document. A breaking migration removes active reservations through normal document save. Retired-protocol snapshots remain stored but are neither imported into current task state nor a supported agent interface.

## Storage and service

SQLite is an internal implementation detail, not a versioned interchange format. Historical database-schema migrations and cross-version snapshot restores are not maintained. Startup creates the current schema for new stores; it does not add missing columns to older stores. An incompatible schema change requires an explicit operator plan to export documents with the matching old build and import them into a separately initialized current store. This policy never authorizes an automatic database reset or deletion of existing storage. Native `.mote` migrations remain supported independently.

- Node.js 22.12+; use `--experimental-sqlite` on the service command (needed on early Node 22, accepted on newer releases). No database package is installed.
- `/var/lib/mote/documents.sqlite`: SQLite WAL, full synchronous commits, document metadata, immutable revisions, deduplicated embedded-image assets, operation acknowledgments, shares, inert assistant state, and workspace settings. Request documents use the same self-contained V1–V9 JSON representation as native documents over the network; image upload delta optimization is not implemented.
- `/var/lib/mote-ai/tasks`: durable task-local execution inputs, outputs, versions, idempotency receipts, Mu sessions, and bounded logs. Server task artifacts are retained after Accept/Discard and are not automatically expired or cleaned up. This is separate from pruning browser-local working-copy caches; local history cannot safely garbage-collect server data because another independent/offline tab may still reference it. No full disk cleanup is implied.
- Retired index descriptions, legacy indexing settings, and leftover index run files are not used or deleted by the current service.
- `/var/backups/mote`: existing private manual SQLite snapshots are preserved. They are same-build operational snapshots, not the portable backup format. No backup runs automatically. Never copy only the live main database file while WAL is active. The existing `server/backup.mjs` uses the SQLite backup API, or `VACUUM INTO` on early Node 22, then checks the result before publishing it.
- `moted.service` listens on `/run/moted/moted.sock`; Nginx is the production authentication boundary. Never expose the service TCP listener or an unguarded private API publicly. Fake development mode is loopback only.
- Workers use their own bind-mounted task directory under a masked task parent. Cloud data, backups, Nginx credentials, and sibling task directories are inaccessible. Worker provider credentials/source/config reads and outbound networking remain intentional trusted-deployment capabilities—not hostile-user isolation.
- All responses retain `Cache-Control: no-store`. Browser recovery is intentional local persistence, not HTTP caching. No service worker.

See `deploy/mote.nginx.conf` and `server/moted.service.example`. Backups are manual only; no backup timer or service is installed. Existing backup files are retained until explicitly removed. Backups are on the same host: they do not protect against loss of that host; copy them elsewhere if that guarantee is needed. Periodic off-host/S3 backups remain a future decision, not an installed schedule. AI execution directories are separate from SQLite backups, so backing up only the database does not back up complete Mu continuation sessions.

### Error diagnostics

Unexpected HTTP 500 failures emit one structured JSON error to the service journal, with `event: "http.unexpected_error"`, `level`, a generated `requestId`, method, route template, status, built-in error type, bounded error code, and up to five server-relative stack locations. Raw URLs, query strings, tokens, document/task IDs, headers, bodies, error messages, and full stacks are omitted. Expected 4xx responses do not generate these error logs.

Responses carry `X-Request-ID`; unexpected 500 JSON also includes `requestId` alongside the generic error. The browser includes a valid reference in connection-error feedback without treating the failed write as acknowledged or retrying generation. Find the corresponding record with `journalctl -u moted.service --since today -o cat | grep -F '<request-id>'`. Keep journal access private; a correlation ID is for diagnosis, not authentication.

### Retention and capacity

Deletion revokes access and tombstones the cloud document; it is not physical erasure of its immutable revisions, embedded assets, or operation acknowledgments. There is no automatic revision pruning or unresolved-task expiry. Preserve those records until an explicit retention/erasure policy accounts for retry acknowledgments and pinned AI inputs. The 128 MiB HTTP body ceiling remains a per-request bound, not a workspace quota; no request rate limit is installed.

Operators can inspect filesystem capacity with `df -h /var/lib/mote /var/lib/mote-ai` and storage usage with `du -sh /var/lib/mote /var/lib/mote-ai /var/backups/mote`. These read-only checks do not open documents or create backups. Review growth before increasing usage; do not delete recovery data to free space without an explicit decision.

### Manual backup

The primary long-term backup is a collection of native `.mote` document exports. Use each document's Share → Export action to download its native `.mote` file when requested. Native files include embedded assets and user Notes; treat them as private data. Keep filenames or an accompanying inventory sufficient to identify the documents. Copy the collection off-host if protection from host loss is needed. There is no scheduled or bulk-export backup workflow installed.

Native exports contain only the native document: they omit cloud revision history, separate reservations, filenames as server metadata, Private/archive flags, share links, workspace settings, indexes, proposals, task tokens, and agent continuation sessions. Server task-artifact retention does not create a compatibility promise; browser-local cache pruning is not server cleanup. HTML and PNG are publication formats, not complete native backups: they omit Notes.

The existing `server/backup.mjs` can still create a consistent SQLite snapshot when explicitly requested. Such snapshots are an optional same-build operational aid; retain the matching application build/schema if they are needed. Do not expect a later build to migrate them.

### Restore

1. Import the requested `.mote` exports through Files → Import. Supported native versions load through the ordinary document migration boundary; imports create fresh cloud document IDs and do not replace existing files.
2. Reapply names and any desired Private/archive metadata explicitly. Exports do not carry access policy; newly imported documents have no public link or external task grant. Verify Private before any sharing or external handoff.
3. Inspect restored content, embedded assets, and Notes. Create new agent reservations or share links only when explicitly requested; old sessions and capabilities are not restored.

For a legacy SQLite snapshot, use its matching application build in an isolated private recovery environment to export documents, then import those exports into the current workspace. A deliberate same-build database restore remains an operator action: stop the service, preserve the existing database and WAL/SHM files, check snapshot integrity, and never combine the restored database with another database's WAL/SHM files. No automatic schema migration, storage reset, backup run, or deletion is implied by recovery.

**V9 release order:** Check active tasks/workers first. Do not mix old API instances with the new reader: an old backend could return a deck before its link is revoked. Successful new backend startup confirms the transaction has committed. No manual document sweep, backup, storage replacement, or re-sharing is required. Do not roll back to an old serving binary without gating public traffic and reviewing its sharing semantics.

Retired protocol artifacts remain stored but are not imported into current task state; no compatibility code or Assistant archive UI is implied.
